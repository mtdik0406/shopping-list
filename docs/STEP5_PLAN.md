## 1. 承認ゲート

- 安全性・整合性に関わる機能は、対応するPoCがPASSするか、代替方式を人が承認するまで完成扱いにしない。Emulatorの結果だけでRISKを閉じない。
- 次は必ず利用者の承認を受ける：Blaze移行、Cloud Billingのリンク、Cloud Functionsの導入、要件・受け入れ条件・UI設計の変更・緩和・延期、Security Rulesの権限拡大、個人データ保持の拡大、30日以内消去目標の扱いの変更、PoCがFAILしたときの代替設計。
- 次は実行前に確認する：GitHubのリポジトリ設定の変更（承認済みのブランチ保護を除く）、Firebaseプロジェクトの作成・設定、Hostingへのデプロイ、本番環境の操作、元に戻せない削除。
- feature branch → PR → CI → レビュー → Squash merge。mainへ直接コミットしない。mergeは利用者が行う。
- 公開リポジトリのため、PR本文・コミット・ADR・試験記録に利用者の実名・続柄・メールアドレス・秘密情報を書かない。

## 5. 進め方

### 5.2 最初のPoCの構成

- Emulatorは`demo-`で始まるプロジェクトIDで起動し、アプリの接続先をEmulatorに固定する（`demo-`の扱いは着手時に公式で確認する）。firebase-toolsはdevDependencyとし、パッケージ管理はpnpm（2026-11-24変更、`DEVELOPMENT_GUIDELINES.md`）。
- 段階1（Node + Vitest + `@firebase/rules-unit-testing` + Web SDK）：Rulesの許可・拒否、トランザクション、同時操作の競合（100回以上）。
- 段階2（Playwright Chromium・WebKit + 永続キャッシュ）：オフライン → 再読み込み → 相手の終了・削除 → 復帰（P01-04・07・08）。WebKitはiOS Safariと同一ではないため、ここだけでPASSにしない。
- 順序：PoC-02（P02-01〜07・09）→ PoC-01段階1（P01-01〜03・05・06・09〜12）→ PoC-01段階2（P01-04・07・08）。
- 結果は`TECHNICAL_VALIDATION.md`の様式（判定・実行日・版・リビジョン・再現手順）で記録し、選んだ方式をADRに書く。
