# TECHNICAL_VALIDATION — 技術検証計画と判定台帳

- 版: v0.9.3
- **実行ステータス：PoC-01〜05すべて未実施。テスト成功、費用0円、30日削除の達成を保証しない。**
- 共通原則: Emulator結果は実機挙動を証明しない。Firebase公式の仕様記述だけでアプリ固有の競合・削除処理を合格としない。

## 判定基準と証跡

各PoCは `NOT_RUN` / `PASS` / `FAIL` / `BLOCKED` を使用。実行日、SDK/ブラウザ/OS、Emulatorバージョン、テストケース、再現方法、ログ、リビジョン、検証者、未解決条件を記録。失敗・未実施のケースがある場合は当該リスクを閉じない。PoC対象以外のACはMVP実装後の受け入れテストで検証する。

## 実施方法

- Emulatorは`demo-`で始まるプロジェクトIDで起動し、アプリの接続先をEmulatorに固定する（`demo-`の扱いは着手時に公式で確認する）。firebase-toolsはdevDependencyとする。
- 段階1（Node + Vitest + `@firebase/rules-unit-testing` + Web SDK）：Rulesの許可・拒否、トランザクション、同時操作の競合（100回以上）。
- 段階2（Playwright Chromium・WebKit + 永続キャッシュ）：オフライン → 再読み込み → 相手の終了・削除 → 復帰（P01-04・07・08）。WebKitはiOS Safariと同一ではないため、ここだけでPASSにしない。
- 順序：PoC-02（P02-01〜07・09）→ PoC-01段階1（P01-01〜03・05・06・09〜12）→ PoC-01段階2（P01-04・07・08）。
- 結果は「判定基準と証跡」の様式で記録し、選んだ方式をADRに書く。
- 実機確認（PoC-03、P02-08）の端末は iPhone（Safari、ホーム画面に追加したPWA）と Android（Chrome、インストールしたPWA）。OS・ブラウザの版は確認時に記録する。

## PoC-01：同時更新・オフライン・リスト終了

対象: RISK-01/02/03/08/09、FR-011〜013/020/025/031〜034/036/037、AC-06〜07、AC-09〜10、AC-13、AC-16〜17、AC-20〜23。

**セットアップ**: EmulatorでユーザーA/B、同じグループ、activeなリストL（商品x1）とofflineを模擬するWeb SDK 2インスタンス。Firestore永続化有無で両方試験。リスト終了後はRulesがitem書き込みを拒否できるかを観測。

| ID | 操作 | PASS条件 |
|---|---|---|
| P01-01 | A/Bが同じ商品を購入済・未購入へほぼ同時に更新 | 最終状態がサーバーで確定した更新に従う（順序の検証方法を証拠化） |
| P01-02 | AとBが同じ商品名を同時追加 | 1商品に合算、数量1〜9、既存担当維持、購入済は未購入へ |
| P01-03 | 合算9+1、商品名編集で重複 | 両方拒否し既存値不変 |
| P01-04 | Aがofflineチェック→Bがonline終了→A復帰 | チェック拒否、L更新なし、未反映通知と操作記録保持 |
| P01-05 | 終了とオンライン編集を競合させる（100回以上を暫定目標） | 終了後確定した編集0件、編集確定が終了前なら整合して残る |
| P01-06 | 同一操作IDで再送/レスポンス消失を模擬 | 操作の二重適用0件、通知状態が決定可能 |
| P01-07 | オフラインで終了を試みる | サーバーで終了せず明示的なonline要請 |
| P01-08 | Aがofflineチェック→Bがonlineで利用中リストを削除→A復帰（FR-037） | チェック拒否、itemsの残存0件、Aに未反映通知と操作記録保持 |
| P01-09 | A/Bが同じ購入先へ表記違い（全半角・大小）の同名定番を同時登録・名称変更・購入先変更（RISK-08） | 重複0件、拒否側に理由通知、既存値不変 |
| P01-10 | Aが追加・合算した直後に取り消し、同時にBが同じ商品を編集・チェック | 最終状態が決定可能でBの確定済み変更を失わない。成立しない場合は取り消しの範囲（自分の直前の追加のみ・確定前のみ等）を人間に提示 |
| P01-11 | 利用中リスト・終了済みリスト・定番から参照される購入先の削除を、A/Bの同時操作（参照の追加と削除の競合）を含めて試行（FR-012） | 参照中は削除0件、参照がなければ削除可、拒否理由を通知 |
| P01-12 | A/Bが前後空白違いを含む同名の購入先を同時登録・名称変更（FR-011） | 重複0件、拒否側に理由通知、既存値不変 |

**技術上の未確定**: Firestore通常書き込みの自動同期と独自outboxの重複制御、サーバー確定順の観測方法、親リストstatusに依存する子itemのRules、Rules呼出し制限。必要なら1商品への操作ログ/専用コマンド文書モデルを比較。

## PoC-02：認証・招待・所属と権限

対象: RISK-07、RISK-10、FR-001〜010、AC-01〜05、AC-24、AC-N03。

| ID | 操作 | PASS条件 |
|---|---|---|
| P02-01 | ユーザーAでグループ作成、B/Cで別々に招待申請 | 承認前は共有データアクセス不可、B/Cの申請は独立 |
| P02-02 | B/C承認を並行実施 | 所属最大2、1承認だけ成立、リンク再利用不可 |
| P02-03 | 有効24時間内に申請後、期限経過し承認 | 承認可能。未申請の期限切れリンクは不可 |
| P02-04 | リンク取消後に承認を試行 | 保留申請も無効、承認不可 |
| P02-05 | 申請者偽装メール/UID、他人の申請取得 | すべて拒否、本人のGoogle emailを管理者へ提示する前に告知 |
| P02-06 | 別グループ参加、管理者偽装、非所属の直接SDK読み書き | 全操作拒否 |
| P02-07 | Bを除外・脱退させる | アクセス拒否、有効商品の担当Aへ、履歴の担当Bは維持 |
| P02-08 | Google RedirectログインをiOS/Androidブラウザ/PWAから実施 | ログイン・復帰・再ログインが動作 |
| P02-09 | 呼び名の参照範囲：申請者の呼び名・メールを管理者以外が読む、非所属者がmembersの呼び名を読む | すべて拒否。所属メンバー同士は相手の呼び名を読める |

**課題**: `users`と`members`の一貫性、Rules `getAfter()`呼出し回数、他ドキュメント参照不在チェック、複数商品に及ぶ担当再割当。Spark+Web SDKだけで安全に成立しない場合は代替設計を人間に提示する。

## PoC-03：PWAオフライン・再接続・性能

対象: RISK-04/07、NFR-001/002/003/007、AC-20〜21、AC-24、AC-N01/02/07。

- iPhone Safari / ホーム画面追加PWA、Android Chrome / インストールPWAを各最新サポート環境で測定。実際のOS/ブラウザ版を記録。初回取得済リストのみofflineで表示・チェック可。未取得リストは表示不可。
- 端末再起動/PWA終了と再起動/タブ複数起動を含める。Firestore永続キャッシュが動く条件と失敗時動作を検証。
- オフライン中にBを除外し、Bが再接続したときサーバー拒否・保存データ無効化が成立するか確認。再接続前の即時消去は要求しない。別GoogleアカウントでログインしてBのキャッシュを読めないことも検証。
- 暫定性能データは30商品と100商品。各端末・条件30回、保存済みリスト表示と購入チェック操作開始〜画面更新のp95<=1000msを目標。同期完了時間とは区別。実機の低速/通常回線、初回/ウォーム時を区別して記録。
- 同期失敗の自動/手動再試行、一時/確定的失敗の状態区分を確認。
- UI（UI_DESIGN.md 第10章）の実機確認を同じ端末で記録する：キーボード表示時に下部の入力欄・定番候補が隠れないか（visualViewport）、日本語変換確定のEnterで追加されないか、画面幅320px・文字サイズ最大での崩れ、丸ゴシックのオフライン表示。

## PoC-04：削除・データライフサイクル

対象: RISK-06/07/09/10、FR-007〜009/026/037、AC-04〜05、AC-17、AC-24、AC-N03/06。

- 有効リスト、履歴、stores、staples、invite+requests、members（呼び名を含む）が存在するグループを作成。利用中リストの単体削除（FR-037）でもitemsの取り残しを検出する。
- 削除開始後の通常アクセス拒否と、Firestoreサブコレクションの取り残しを検出。
- 故意の通信断、ページクローズ、再ログインで削除処理を中断し、再開または運用側回復まで完遂するか検証。
- グループ削除後の管理者アプリアカウント削除/メンバー脱退後削除、再認証、不要個人データ削除を確認。
- Firestore/Authentication/Hosting・監査ログ・バックアップの保持仕様を**公式ソースごとに列挙**し、30日以内削除目標の達成可否を判定。不可の場合は制約を明示してユーザー承認を取る。

**ブロッカー**: Webクライアントからのサブコレクション完全削除は公式に非推奨で、ブラウザ終了後の自動完走も未証明。Spark制約を守って実現できなければ別方式/Blazeを提案し、承認前に実装済みと主張しない。

## PoC-05：Spark運用費・上限

対象: RISK-05、NFR-005、AC-N05。

- リアルタイム監視1人/2人、リスト30/100商品、再接続、Rules参照、同期リトライのread/write/delete実測。
- 10/100/1000グループのシナリオについて月間操作頻度の**仮定を明記**して数量計算。無料枠の消費と超過時の挙動を確認。
- Hosting通信量、Auth条件、無料枠、Firebaseプロジェクト作成可能数・使用量監視、上限通知可能性を公式仕様で確認。
- SparkからBlazeへの自動移行禁止。課金アカウントのリンク操作も承認対象。予算アラートだけで支出が止まると誤認しない。

## 実装開始・判断条件

- 本書はPoC失敗の許容や本番公開の承認ではない。
- **安全性・整合性を担保する機能**は対応PoCをPASS、または代替方式を人間が承認してから完成扱いとする。
- Blaze課金、MVP要件削減・緩和、30日目標の扱い変更は必ず再承認。
- 商品・定番の重複判定に使う正規化キー（nameKey）は、Security Rulesで名前から再計算できない。グループ所属者が改変したクライアントで重複を作り得ることは、2人のグループ内に閉じた残余リスクとして受容する。PoC記録とADRに明記する。
