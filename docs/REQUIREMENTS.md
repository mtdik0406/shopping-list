- 版：v2.2

## 1. 目的・MVP完成の判定

開発者と家族の2人が、紙なしで買い物前の準備、購入担当の分担、買い物中の購入チェック、終了、次回準備まで完結できることを目指す。Googleアカウントを持つ一般利用者も、それぞれ独立した2人以下のグループで利用できる。

本書は利用者に提供する振る舞い・業務ルールを定義する。実装構造、画面配置、API、データベース設計は確定しない。機能の受け入れ判定は`ACCEPTANCE_CRITERIA.md`を参照する。実利用上の成功基準（2週間紙に戻らない、開発者と家族の双方が便利かつ継続希望と評価）は企画書に従い、機能テストの合否と区別する。

## 2. 用語

| 用語 | 定義 |
|---|---|
| 利用者 | Googleアカウントで認証したアプリ利用者 |
| 呼び名 | 利用者が設定し、同じグループの相手に表示される名前。各端末では自分を「自分」、相手を呼び名で表示する |
| グループ | 共有データを扱う単位。最大2人、1利用者1グループ |
| 管理者 | グループ作成者。招待・除外・グループ削除権限を持つ |
| 一般メンバー | 招待申請が承認された利用者。通常の買い物操作は管理者と同等 |
| 購入先 | 「スーパー」「ドラッグストア」等、グループで登録する自由名称の区分。個別店舗の所在地・在庫は管理しない |
| 定番商品 | 購入先ごとに保存し、次回以降リストへ再利用する商品名と、いつもの数量 |
| 買い物リスト | リスト名・購入先1つ・商品と数量・担当者・購入状態を持つまとまり |
| 利用中・終了済み | 更新可能なリスト・履歴として閲覧専用となったリスト |
| 未同期変更 | 端末に保持され、サーバー上の共有状態への反映が完了していない購入チェック |
| 確定的な同期拒否 | リスト終了・権限喪失等により、未同期変更をサーバーに反映できない状態 |

## 3. 機能要件

本節のFR-001〜037はすべて**MVP必須の業務仕様**。

### 3.1 アカウント・グループ

| ID | 要件 |
|---|---|
| FR-001 | Googleログイン・ログアウトができる。初回ログイン時にアプリ利用者を登録し、同じGoogleアカウントで機種変更後も利用を再開できる。 |
| FR-002 | 認証済み利用者はグループを作成でき、作成者が管理者になる。作成時に呼び名を設定する（初期値はGoogleアカウントの表示名、後から変更可）。1利用者は最大1グループにしか所属できない。 |
| FR-003 | 1グループは最大2人。所属しないグループの共有データは閲覧・変更できない。 |
| FR-004 | 管理者は発行から24時間有効で参加成立1回限りの招待リンクを作成・任意の方法で共有できる。有効期間内には異なる利用者から複数申請を受け付けられる。期限切れ・使用済みリンクから新規申請はできない。 |
| FR-005 | 招待リンク利用者はGoogleログイン後に明示的に参加申請できる。申請前にGoogleアカウント由来のメールアドレスを管理者へ共有すると知らせる。申請時に呼び名を設定する（初期値はGoogleアカウントの表示名、後から変更可）。管理者は当該メールアドレスと呼び名で申請者を識別し、承認・拒否できる。承認前は共有データにアクセスできず、同じ利用者・同じリンクの重複申請を作らない。 |
| FR-006 | 有効期間内に行った申請はリンク失効後も承認・拒否できる。管理者がリンクを取り消すと関連する承認待ち申請も無効。複数申請のうち最初に承認が成立した1人のみ参加でき、同時承認でも最大2人とリンク1回限りの制限を守る。参加成立後のリンク再利用は禁止。 |
| FR-007 | 管理者は一般メンバーを除外でき、一般メンバーは脱退できる。操作前に確認する。成立時から対象者によるサーバー共有データへのアクセスを拒否し、端末の保存済み共有データは次回オンライン接続時に無効化する（オフライン中の即時消去・閲覧禁止は保証しない）。利用中リストの脱退者担当商品は残るメンバーに再割り当てし、終了済み履歴は変更しない。その他の共有買い物データはグループに残す。 |
| FR-008 | 管理者だけが確認後にグループを削除できる。リスト・履歴・定番商品・購入先等の共有データを削除し、アプリからの復元機能は提供しない。管理者自身の脱退はできない。 |
| FR-009 | 利用者は確認後に自分のアプリアカウントを削除できる。一般メンバーは脱退後、管理者はグループ削除後に可能。呼び名を含む不要な個人データを通常利用データから削除しアプリアカウントのアクセスを停止した時点で操作完了とする。必要な共有データは維持。バックアップ・ログはNFR-006で扱う。Googleアカウント自体は削除しない。 |
| FR-010 | 通常のリスト・商品・購入先操作の権限は2人で同じ。招待・メンバー除外・グループ削除は管理者だけが行える。 |

### 3.2 購入先・定番商品

| ID | 要件 |
|---|---|
| FR-011 | グループ内で購入先を自由な名前で追加・名称変更でき、双方に共有する。名称は前後空白を除去した1〜50文字で必須。同じグループ内で前後空白除去後の同名登録は禁止。スーパー等の固定種類に限定しない。購入先にはアプリが用意したアイコン（12種）から1つを設定・変更でき、未設定時は既定のアイコンを表示する。 |
| FR-012 | 両メンバーが購入先を追加・名称変更・削除できる。ただし**利用中リスト・終了済みリスト・定番商品のいずれかから参照される購入先は削除できない**。参照がなければ削除できる。 |
| FR-013 | 定番商品を商品名・購入先・いつもの数量で直接登録・編集・削除できる。名前は前後空白除去後1〜100文字。いつもの数量は1〜9の整数で初期値1。担当者の既定値は保存しない。各定番商品は購入先1つに属し、異なる購入先なら同名登録を許可する。同じグループ・購入先では正規化後の商品名が一致する重複を、直接登録・リストからの登録・商品名変更・購入先変更のすべてで禁止し、理由を通知して既存値を変更しない。購入先変更は許可する。比較はFR-019の商品名正規化方針を共通適用する。 |
| FR-014 | 定番商品を編集・削除しても、既にリストへ追加した商品名・数量・担当者・購入状態は変更しない。削除前に確認する。 |
| FR-015 | リストの購入先に対応する定番商品から必要なものを選び、リストに追加できる。追加時の数量の初期値は定番のいつもの数量、担当者の初期値はFR-022に従う。数量・担当者は追加後に変更できる。 |
| FR-036 | 利用中・終了済みのどちらのリストの商品も、購入状態を問わず定番商品へ登録できる。登録先はリストが参照する現在の購入先（登録時に別の購入先へ変更しない）。終了時の購入先表示名と現在名が異なる場合も現在の購入先を使用する。商品名と購入先を保存し、いつもの数量は1で登録する（後から変更可）。リスト商品の数量・担当者・購入状態は保存しない。元リスト・履歴は更新しない。FR-013の重複禁止を適用し、重複時は登録しないで理由を通知する。既に参照先が存在しない異常データの場合は登録先の選択を求めるが、通常操作で参照中購入先を削除することはFR-012により禁止される。 |

### 3.3 買い物リストと商品

| ID | 要件 |
|---|---|
| FR-016 | リスト名と購入先1つを持つリストを作成し、複数リストを並行して利用・切替できる。リスト名は前後空白除去後1〜50文字で必須。 |
| FR-017 | 利用中リストの購入先は変更できる。変更しても既存商品名・数量・担当者・購入状態を保持し、変更先購入先との商品内容一致は強制しない。 |
| FR-018 | 利用中リストに単発商品を追加・編集・削除できる。名前・数量・担当者を変更でき、削除前に確認する。名称編集により同じリストの既存商品と重複する場合は拒否・通知し、自動合算しない。 |
| FR-019 | 商品名は前後空白除去後1〜100文字、数量は1〜9の整数（初期値1）、単位管理なし。商品名の重複判定では前後空白を除去し、全角・半角・大文字・小文字の違いを正規化して同一視する。Unicode正規化の具体方式・文字数計数等は設計時に検証する。 |
| FR-020 | 同一リストへ同一商品を追加すると別行を作らず数量を合算し、既存担当者を維持する。合算後の数量と担当者を示す。合算後も1〜9の範囲を守り、超過する追加は拒否・通知して保存しない。 |
| FR-021 | 購入済み商品へ同一商品を追加したときは数量合算後に未購入へ戻す。購入済み数量の個別管理はしない。 |
| FR-022 | リスト商品の担当者は所属メンバーのいずれかを必須とし、担当なしでは登録できない。追加時の初期値は表示中の担当の人（「すべて」表示時は操作者自身）とする。買い物中も変更可能で代理購入に対応する。 |
| FR-023 | リストを開いたとき自分の担当商品を初期表示し、相手担当および全員分（すべて）へ切り替えられる。「すべて」では各商品の担当を示す。未購入・購入済みを区別し、双方ともチェック変更できる。 |
| FR-024 | カゴに入れた時点で商品単位に購入済みとし、チェック取り消しで未購入へ戻せる。数量は変えない。 |
| FR-025 | 利用中リストはオンラインで手動終了できる。終了前に他端末の未同期変更が反映されない可能性を警告して明示的確認を要する。終了済みリストは閲覧専用で、商品追加・編集・削除、担当変更、購入チェック、購入先変更、再開を禁止する。空リストも終了可能。FR-036による別データの定番商品作成は履歴編集に該当しない。 |
| FR-026 | 終了済みリストは手動削除するまで期限なく履歴保持する。終了時の購入先表示名を固定し、後日の購入先名称変更は履歴表示へ反映しない。履歴の手動削除は確認を要し、削除後の参照・引き継ぎはできない。 |
| FR-027 | 任意の利用中または終了済みリスト**1件**の未購入商品から必要なものを選び、**新規リスト**へ商品名・数量・担当者をコピーできる。コピー先は未購入とし、元リストは変更しない。 |
| FR-037 | 利用中リストも確認後に手動で削除できる。削除は元に戻せず、削除後は閲覧・引き継ぎできない。他メンバーの端末から削除後に届いた変更はFR-034と同様に拒否し、未反映を通知する。 |
| FR-028 | 未購入商品の引き継ぎ先は元リストと同じ購入先の新規リストのみ。既存リスト・別購入先への引き継ぎ、複数リストをまたぐ一括引き継ぎは対象外。 |

### 3.4 共有・オフライン・競合・例外

| ID | 要件 |
|---|---|
| FR-029 | グループ内の2人はオンラインで同じリスト内容・担当者・購入状態を共有し、反映済み変更を互いに確認できる。 |
| FR-030 | 事前保存済みリストはオフラインでも閲覧・購入済み／未購入の切替ができる。初回取得・未保存リストには通信が必要。オフラインでの商品追加・編集・削除、定番登録はMVP必須ではない。 |
| FR-031 | 未同期の購入チェックを端末に保持し、通信回復後に自動同期する。一時的失敗では破棄せず自動再試行・手動再試行できる。保留・失敗・確定的拒否を区別して通知し、終了済み・権限喪失による拒否を成功扱いしない。 |
| FR-032 | 同一商品の購入チェック競合は、端末操作時刻ではなくサーバーで**最後に確定した更新**を採用する。順序の一意性・再送時の扱いはRISK-02で検証する。 |
| FR-033 | オンラインでのリスト終了時、他端末の未同期状態が不明でも、未反映の可能性を警告し利用者が確認すれば終了できる。全端末同期完了証明は要件としない。終了との競合はRISK-01で検証する。 |
| FR-034 | サーバーで終了確定後（またはリスト削除後）に届く変更（通常編集・遅延購入チェック）は拒否し、終了済みリストを変更しない。未反映チェックについては利用者に通知し、通知前に黙って破棄しない。終了との原子的整合性はRISK-01・03で検証する。 |
| FR-035 | 空状態、操作失敗、通信・同期エラー等では状況と復旧の手がかりを示し、再試行可能な操作には再試行手段を提供する。 |

## 4. 非機能要件（NFR）

| ID | 要件・水準 | 判定・検証上の留保 |
|---|---|---|
| NFR-001 | iPhone・Androidの主要な現行ブラウザで利用可能なPWAとする。 | 対象OS・ブラウザ・バージョンの表は後工程で決定して実機確認。 |
| NFR-002 | 事前保存済みリストの表示と購入チェックの画面反映を、通常の通信環境・測定データで**1秒以内とする目標**。 | サーバー同期完了時間ではない。測定開始／終了点、端末、件数、分位点は未確定。 |
| NFR-003 | グループ間を分離し、非所属者のサーバー上の閲覧・更新を防ぎ、管理者操作を限定する。共有解除後の端末保存データは再接続時に無効化する。 | オフライン中のキャッシュ即時消去・閲覧禁止は保証しない。 |
| NFR-004 | 操作結果、空状態、通信断、失敗、保留、復旧方法が分かる。読みやすい文字、押しやすい操作領域を重視する。 | 具体的なUIと操作性は後工程で検証。 |
| NFR-005 | 運用費原則月額0円を**目標**とし、費用が発生する変更は事前に人間が判断する。 | Firebase等の無料枠内運用は保証しない。料金・上限・監視を検証。 |
| NFR-006 | アカウント削除時、通常利用データから不要な個人データを速やかに削除する。バックアップ・ログ残存データは最大30日以内の消去を**目標**とする。 | 法令、基盤の保持仕様、消去対象・時点・証跡を検証。30日は保証値ではない。 |
| NFR-007 | 端末内の未同期購入チェックを保持して復帰時に同期することを目指す。 | 端末・アプリ削除によるデータ喪失は保証しない。終了・権限喪失時の拒否はFR-031・034に従う。 |

## 5. 共通業務ルール・境界条件

- 名前の長さ：購入先・リストは1〜50文字、定番商品・リスト商品は1〜100文字（前後空白を除去した後）。空白のみは禁止。数量は整数1〜9、初期値1。担当者は必須。
- 商品名の同一視：前後空白・全角半角・大小文字の差を正規化し、リスト内の同一商品判定および同一購入先の定番商品重複判定に使用する。実際のUnicode正規化・ケースフォールド・空白種別・文字数の計数方法は、これらの期待動作を満たすよう設計時に決定する。
- 購入先名の重複禁止：既存FR-011どおり前後空白を除去した名称で判定。商品名と同じ追加正規化ルールを自動適用するものではない。
- 登録・名称変更・購入先変更が重複で拒否された場合、変更前のデータを残す。同時操作による定番商品重複防止の実現性はRISK-08で検証する。
- 終了済みリストでは元のデータを変更しない。リスト外に新しく定番商品を作る行為、および元の未購入商品の新規リストへのコピーは許可する。
- 通常のアプリ操作では参照中の購入先を削除できない。参照が壊れた異常データからの定番登録時には登録先選択を求める方針だが、回復方式の具体化は後工程で扱う。
- 終了済みリストは無期限に保持するが、利用者による手動削除・グループ削除・必要なデータ削除ルールは例外となる。

## 6. MVP対象外

- 価格・予算の管理・集計
- レシート読み取り（OCR）・バーコード読み取り
- AIによる商品推薦、プッシュ通知
- 個別店舗の所在地・在庫・個別店舗ごとのリスト管理
- 購入済み数量の個別管理
- 複数リストを横断する一括引き継ぎ、既存リストへの引き継ぎ
- 終了済みリストの再開
- 管理者権限の移譲、複数グループ所属
- アプリ独自のパスワード・パスキー認証
- 保存済みリストの閲覧・購入チェック以外のオフライン編集・定番登録の保証

MVP機能の延期・削除や対象外範囲の変更は、人間の明示的承認なしに行わない。

## 7. 技術的リスクと検証ゲート

以下は**実装前・設計時に検証する課題**であり、業務仕様の未確定や実現済みを意味しない。検証で仕様変更が必要になれば利用者の承認を得る。

| ID | 対象 | 未検証の事項・必要な検証 |
|---|---|---|
| RISK-01 | FR-025、033、034 | オンライン終了と他端末未同期操作が競合した場合の終了後更新拒否・未反映通知・整合性をPoCで検証。 |
| RISK-02 | FR-020、032 | サーバー確定順、同時チェック変更・追加・再送時の一意性、数量上限・重複行防止。 |
| RISK-03 | FR-034 | 終了・通常編集・遅延同期の原子的な境界と終了済みデータの不変性。 |
| RISK-04 | NFR-002 | 1秒目標の測定条件（端末・件数・計測点・割合）と実測。 |
| RISK-05 | NFR-005 | Firebase等の料金、想定利用量、無料枠超過時の検知・判断。 |
| RISK-06 | FR-009、NFR-006 | 削除対象情報と、ログ・バックアップの保持・30日以内消去目標への適合。 |
| RISK-07 | FR-007、009、NFR-003 | 除外・脱退・削除後のサーバーアクセス拒否と再接続時の端末保存共有データ無効化。 |
| RISK-08 | FR-013、036 | 同じ購入先への定番商品の同時登録・名称変更・購入先変更、正規化表記違い、再送が競合しても重複を生まないこと。拒否操作を成功扱いせず通知すること。 |
| RISK-09 | FR-037 | 利用中リストの削除と、他端末の未同期操作・終了との競合時の拒否・通知。RISK-01・03と合わせてPoC-01で、削除後の残存データはPoC-04で検証。 |
| RISK-10 | FR-004〜010 | Web SDK＋Security Rulesだけで成立するグループのライフサイクル（同時承認、脱退・除外時の担当再割当、グループ削除の完了性）。PoC-02・04で検証。 |

その他の設計時確認：対象ブラウザ、Unicodeの文字数・正規化方式、PWAの端末保存動作、UX、運用手順、費用等。Figma・Storybookの具体的な使い方は後工程。

## 8. 受け入れ・トレーサビリティ

- `ACCEPTANCE_CRITERIA.md`は主要な**25件の業務シナリオ**（AC-01〜AC-25）と、各シナリオに必要な補足判定条件で構成する。件数を減らすことは既存業務ルールの削除を意味しない。
- FR-001〜037の各要件は少なくとも1つの主要受け入れシナリオへ対応付ける。NFR-001〜007は別の検証観点を保持する。
- 文字数境界値、正規化の細目、招待の並行承認、同期・終了競合、ブラウザ実機試験等は詳細テスト・リスク検証として扱う。業務上必須の期待動作は受け入れ補足条件にも残す。
- 技術リスクを検証する前に受け入れテスト全体の合格・リリース可能とは判定しない。
