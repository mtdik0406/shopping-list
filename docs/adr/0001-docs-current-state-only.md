# 0001. 文書には現在の決定だけを書く

- 状態：承認
- 日付：2026-11-25
- 関連：全文書（`docs/`）

## 背景

`docs/` の文書は、企画から実装準備までの工程（STEP 1〜5）ごとに作られ、本文に工程・承認状態・改訂記録・変更管理（CM）の経緯を含んでいた。そのため、ある事実を変えると複数の文書の経緯の記述も直す必要があり、現在の決定がどれかを読み取りにくかった。

## 選択肢

1. 経緯を本文に残したまま、文書ごとに改訂記録を足していく。
2. 本文には現在の決定だけを書き、経緯はgitの履歴・PR・ADRに任せる。

## 決定

選択肢2を採る。

- 本文から工程（STEP）・承認状態・改訂記録・変更管理の経緯を除く。
- mainへのmergeをもって、その文書の内容を承認したものとする。
- 未検証の事項は、検証結果を記録するまで未検証と明示し続ける。
- 要件・受け入れ条件などのID（FR・NFR・AC・RISK・PoC・S-xxなど）は変えない。

整理前の基準は、コミット `ff16431`（文書どうしの版番号の参照をなくした時点）とする。その時点の各文書の版と承認状態は次のとおり。経緯の詳細はそのコミットの各文書の改訂記録・承認記録と、`CHANGE_REQUESTS_STEP2.md`・`STEP5_PLAN.md` を参照する。

| 文書 | 版 | 承認状態 |
|---|---|---|
| `PRODUCT_BRIEF.md` | v1.2 | 承認済み（v1.0、2026-11-23）。v1.1・v1.2は表現と参照の更新 |
| `REQUIREMENTS.md` | v2.2 | v2.1を2026-11-24に承認。v2.2（CM-11の反映）はPR #1のmergeで確定 |

「条件付き承認」の条件（安全性・整合性に関わる機能は、対応するPoCがPASSするか代替方式が承認されるまで完成扱いにしない）は、整理後も `TECHNICAL_VALIDATION.md`「実装開始・判断条件」と `ARCHITECTURE.md` 第1章・第10章に残す。

## 根拠

- 経緯はgitの履歴とPRに残り、本文から消しても失われない。
- 現在の決定だけを書けば、変更時に直す箇所が減り、読む人が現在の決定を取り違えにくい。

## 影響

- `DEVELOPMENT_GUIDELINES.md`「文書の書き方と改訂」にこの規則を書く。
- `CHANGE_REQUESTS_STEP2.md` と `STEP5_PLAN.md` は、含まれる決定をADRとIssueへ移したうえで廃止する。

## 見直し条件

- 経緯を本文で参照しないと要件や設計を正しく読めない場面が出たとき。
